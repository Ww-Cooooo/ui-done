# Clarify Feedback Before Choosing a Revision

Load this guide when the user requests clarification, or feedback or an uncertainty discovered during frontend work leaves materially different plausible revisions. It covers remarks such as “not premium enough,” “feels AI-generated,” “the animation is wrong,” or “still not what I meant.” Those phrases are signals to investigate, not automatic questionnaire keywords. Repeated overall rejection with an unresolved cause requires clarification before another concept build or delegation. This guide works from the user's brief and available artifact without the UI Done development conversation or any other installed Skill.

## Route once, then keep designing

When `clear-feedback` is available, read and use it for the clarification conversation. Use the handoff below to bring its result back into UI Done. When it is absent, use this guide directly; no installation, nested Skill discovery, network request, special question tool, or host-specific command is required. Do not claim the companion ran when only this fallback was used. With both available, use one conversation and one set of answers, not two passes of the same questions.

Carry the user's requested interview depth into that route. A companion's ordinary stop condition for choosing the next revision does not finish an explicitly requested in-depth interview. Apply this guide's branch method and completion criteria to that same conversation, including when the companion is available; do not leave them only in the unavailable-companion fallback.

UI Done continues to own frontend selection, design, implementation, and verification. Clarification does not waive its required capabilities, authorize a rewrite or deployment, or guarantee that every host automatically loads a Skill it has never exposed. Once UI Done is active, this route applies during review and revision as well as at prompt intake.

## Decide whether an answer is actually needed

Inspect the available artifact, affected action, confirmed requirements, and references first. Keep three things separate: an observable defect, the user's reported feeling, and your hypothesis about its cause. If the artifact or dynamic state is unavailable, say what cannot be inspected rather than invent observations.

- **Specific instruction or reproducible fault:** act within the existing authorization. Covered text, a mislabeled selected tab, or a button that cannot save needs investigation or correction, not a taste interview.
- **Several interpretations with different consequences:** load this route and identify the missing preference that distinguishes them. For example, “not smooth” could mean dropped frames, abrupt state changes, excessive scrolling inertia, or an unwanted visual style. Diagnose measurable failures; ask about the remaining preference rather than guessing it.
- **Enough context for a low-cost, reversible comparison:** explain the specific hypothesis and make a focused sample within scope when that comparison can resolve the remaining distinction. This does not override an explicit request to clarify first or repeated overall rejection whose cause remains unresolved. Prior references, a list of rejected patterns, permission to continue, and reversibility alone do not establish the desired direction. If the user cannot describe a preference, a small reference/visual comparison can be part of the clarification conversation; it is not permission for another speculative full redesign.
- **Mixed feedback:** fix confirmed defects where authorized while clarifying the uncertain direction. A taste question should not block unrelated corrections, and a technical fix should not be presented as resolving the taste complaint.

Do not ask again for a preference already answered. If a new answer conflicts with a prior constraint, identify the conflict before treating either as permission to change the product.

## Ask about what the user can recognize

Briefly explain the visible difference that makes the answer useful, then ask the questions that resolve it. A small question set is a per-round choice, not a limit on total rounds. Keep asking responsive follow-ups while the intended result remains insufficiently understood; do not stop because a few questions were answered, you feel "close enough," or you want to return to implementation. Use each answer to narrow the next question rather than restart a questionnaire. Professional implementation decisions remain the designer's responsibility, not questions the user must answer.

Anchor questions to the current screen, an actual action, or a small comparison. Use ordinary language, not library names, easing constants, or a request for the user to design the layout. Let the user combine answers, reject all suggestions, say “I cannot describe it,” or provide an example. Suggested choices are hypotheses, not a closed menu of styles.

### When the user requests an in-depth interview

Map the consequential decisions within the agreed task: what is already confirmed, what remains open, and which later choices depend on each open answer. Do not shrink the agreed interview to only the latest complaint or the next sample. Use the original brief and available work to establish facts first. Do not invent an exhaustive product specification, restart settled background questions, or turn professional implementation choices into user homework.

Ask one concrete question at a time, or a small set whose answers are independent. Give your recommendation and its basis while allowing a different answer; for reported impressions, offer neutral distinctions rather than recommend how the user should feel. Resolve prerequisites before asking dependent questions; do not assume an unanswered choice to make a later question easier. After each answer, update which branches are settled or newly exposed, and continue with those now answerable. A broad label such as “working feel” or one local complaint may resolve one branch while leaving others open.

For example, a workspace that looks like a portfolio may need a different balance between reviewing the whole source, inspecting a troublesome moment, and recording an actionable opinion. First check what the brief and real workflow already establish. Ask about the remaining concrete working situation, then use that answer to investigate the relevant picture, sound, time, or opinion relationship. Do not jump from “working feel” directly to dark colors, a familiar editor layout, or a full editing product. These are possible branches, not a questionnaire to repeat for every workspace.

When the unresolved rejection concerns the whole visual design, workflow answers establish constraints rather than visual agreement. Clarify the consequential composition and visual-identity distinctions as well as the relevant action state; do not let a well-ordered workflow interview avoid the quality actually being judged. When words are insufficient, present professionally developed, numbered visual alternatives using the same representative content. Make their spatial, typographic, surface, and action-state differences recognizable without asking the user to design the layout or fixing a proposal count. The user may combine qualities or reject all options. A selected direction settles only those differences, not every remaining design decision. Follow `../SKILL.md`'s default design-first sequence for new pages and substantial redesigns: refine and confirm the representative drafts before frontend implementation, then implement and refine the agreed functionality. A design choice, approval of a draft, and acceptance of its implementation remain distinct.

“We can make the next sample” is a stage decision, not closure of the interview. If the user chooses a sample to answer an experience question, state which question it addresses and retain the other open branches; use the response to resume them. Finish the agreed interview only under the confirmation criteria below. Reopen affected branches when new rejection or a conflicting answer appears, rather than beginning a fresh generic survey.

Method basis: [GRILL-ME's grilling method](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/productivity/grilling/SKILL.md) and [its usage guidance](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/docs/productivity/grill-me.md). This adaptation keeps prerequisite-aware follow-ups and shared-understanding closure within the frontend task; it requires neither the external Skill nor a fixed question count, and ordinary explicit fixes still use the direct route above.

If words do not resolve the distinction, offer a small visual or interactive comparison using the same content and task. Explain what differs and avoid a deliberately weak option that makes your preferred design win. For a motion complaint, a static screenshot alone is not a useful comparison; show the relevant transition when tools and authorization allow it. Only if the user explicitly chooses to delegate the open taste decisions or try that comparison may you proceed with the stated assumptions in that scope; do not infer this choice from a bare “continue” or present it as completed understanding.

## Confirm understanding, then return to design

In the existing task context, retain a short revision brief: the actual result objective, decisive original user words, what the user rejects or wants to retain, your recommended change and its rationale, unresolved assumptions, and the concrete scene/action that will reveal improvement. When a reference is selected, retain its exact accessible artifact/state and the [concrete transfer decisions](open-source-ui-sources.md#preserve-concrete-reference-evidence), not just a style label or a summary of the conversation. Separate confirmed preferences from observed traits and proposed adaptations. No new report, permanent preference file, or formal approval round is required.

For example, “more premium” may become: “Keep precise playback immediate. When opening a note, make the selected subject and its note remain visibly connected through the space change; remove redundant action choices. The user rejects page-wide entrances and slower seeking.” These preferences are hypothetical: record them only if the user's answers support them, not as defaults assigned to anyone asking for polish. After the user confirms this concrete understanding, it supports that agreed scoped candidate, not a universal template or permission to change storage semantics.

Before leaving clarification, restate the intended result in concrete, ordinary language and let the user confirm or correct it. It must faithfully cover the relevant desired impression or behavior, what is rejected and retained, what transfers from a selected reference, and the change the next result should make visible. These are checks on your understanding, not a fixed form or a requirement to ask about facts already established. If you still need to guess between consequentially different designs, if the user corrects your restatement, or if an answer merely repeats “premium” or “not AI-looking,” continue with the unresolved distinction. Neither accepting a reference without its caveat nor a bare “okay, continue” before a concrete restatement settles that distinction. Do not claim complete understanding solely from your own confidence.

Leave clarification only after the user confirms that the restatement accurately captures what they want and no unresolved preference would materially change that agreed direction. If the user explicitly chooses to delegate the remaining taste decisions or try a comparison instead, state those open assumptions and proceed only within that choice; do not label them understood or accepted. Do not demand CSS values, engine choices, or exhaustive future states to establish understanding. Preserve the answers, the user's clarification-first request, and any open assumptions through an authorized handoff or continuation, without turning a one-project preference into a rule for every user. If the next result is rejected again, return to the remaining distinction rather than defend library coverage. A confirmed understanding of the brief is not acceptance of the resulting design.

## Worked examples

### “动画还是没有高级感” — the animation still lacks polish

Suppose a review workspace has a panel fade-in and a smooth transcript list. Those facts do not establish what the user dislikes. A useful opening is: “我看到现在主要是表单淡入和列表滚动。你更不满意的是操作时几乎感觉不到变化，变化生硬不连贯，还是页面本身不好看、加动画也没用？可以同时选，也可以说都不是。”

If the answer is “每个部分各动各的，像拼起来的,” focus the next candidate on the relationship across selection, contextual editing, and completion, using the [motion sequence method](motion-scroll-and-3d.md#design-a-sequence-not-a-tween-quota). Do not merely lengthen every animation. If the answer is “整个布局都不想要,” establish what functionality must survive and use the [redesign method](page-composition.md#repair-a-rejected-layout-family), not another layer of polish. If a favorite reference is provided, ask or infer from the stated comparison which quality transfers; it does not authorize copying its entire product or adding unrelated effects.

### “这个标题被挡住了，移开图标” — an explicit defect

The requested correction is already clear. Inspect the overlap, repair the responsible layout in scope, and check the affected state. Do not launch the interview just because the same user previously said “AI-generated.”

### “产品页太普通了” — the product page feels generic

Suppose the page works, but it could advertise almost any product after changing the name. Distinctive typography, a subject-led composition, and a more theatrical interaction are different possible revisions. Ask which existing moment or reference captures the desired impression, offering a concrete comparison if the user cannot name it. If the answer is “想让人先看清商品细节，不是看一堆宣传卡片,” organize the next sample around the real product and its details; do not infer that the user also wants dark colors, 3D, or a pinned scrolling sequence.

### A public showcase is rejected repeatedly

Passing playback and saving tests does not establish a convincing public demonstration. If it is still unclear whether the rejection concerns the first impression, interaction flow, or visual identity, ask about that difference before another full build. Demonstrate the proposed direction with a representative sequence before extending it; do not compensate for uncertainty by adding more panels, effects, approvals, or a large benchmark suite. Keep the current result labeled as a candidate rather than presenting it as the accepted showcase.

For example, “the whole screen looks ordinary” is not resolved by learning that the user rejects cards and likes two reference images. Ask what they respond to in those references, especially if they warn that the background may be the only attractive part. If they reply “I still cannot explain it,” compare a concrete difference in subject scale, typography, spatial relationships, or the actual transition without requiring design vocabulary. If they then identify a preferred difference but reject your proposed transfer, keep clarifying that transfer. Only move into the next concept after your concrete restatement is confirmed; selecting two images or answering two rounds is not itself the stopping condition. This is an illustrative conversation, not a prescribed visual style.
