# Clarify Feedback Before Choosing a Revision

Load this guide when the user requests clarification, or feedback or uncertainty discovered during frontend work leaves materially different plausible revisions. Repeated overall rejection with an unresolved cause calls for clarification before another full concept build or delegation, not an automatic long questionnaire. Work from the actual brief and available artifact. If Get Clear is unavailable, this guide is a complete fallback and needs no development conversation, extra Skill, or special question tool.

## Route each feedback, then return to design

When `get-clear` is available, load it before changing the artifact. It owns the user-facing interview, the exact next-question and option check in `get-clear/references/questioning.md`, and the final requirement-understanding report and explicit approval loop; for repeated rejection, follow `get-clear/references/repeated-feedback.md`. After an active Get Clear interview, UI Done supplies inspected UI facts and technical evidence, then resumes the same revision only after the user approves the current complete report or explicitly changes the process. User additions update only affected open points and the report; they are not report approval. Put every operation within that revision in the report before carrying it out. A separate, independently authorized small edit follows its direct route and neither counts as report approval nor waits for an unrelated report. Do not run a second interview or use this guide to shorten Get Clear's clarification. Otherwise use the standalone fallback below; do not claim Get Clear ran when it was unavailable.

Honor the user's **current** requested depth and pace. An explicit in-depth interview warrants prerequisite-aware follow-ups; it is not permanent authorization to interview after the user asks to see drafts, delegate taste decisions, or stop. Conversely, do not silently abandon a requested clarification-first stage to build another application. Neither clarification nor a liked reference authorizes a rewrite, integration or deployment.

## Standalone clarification fallback when Get Clear is unavailable

Use the following question process only when Get Clear cannot be loaded. Reassess each answer, including a question-tool answer returned in the same long turn. For repeated rejection, all-selected defect lists or inability to describe a preference, keep only actual clues, inspect the rejected screen and ask one recognizable result distinction. Do not ask whether to interview or who should find references. Shared traits of rejected versions are possible causes, not confirmed dislikes; universally desirable improvements do not distinguish a preference.

## Decide whether an answer is actually needed

Inspect the available artifact, affected action, confirmed requirements and selected references first. Separate observable defects, the user's reported feeling, and your causal hypothesis. If a screenshot or dynamic state is unavailable, name that limit rather than inventing observations.

- **Specific instruction or reproducible fault:** an independent explicit small edit or fault can use the direct route. If the operation belongs to the same revision being clarified, include it in the report and wait for approval; do not let an unrelated direct repair approve or block that revision. Covered text or a button that cannot save does not require a taste interview when it is the task at hand.
- **An apparently concrete answer with an unresolved meaning:** check its key term, referent, degree and premise against the actual screen and previous question. “Less decoration” might refer to extra ornaments, emphasized controls or motion; do not silently translate it into removing all of them. If context settles it, reuse that meaning. Otherwise compare one observed instance with another plausible referent and ask what the user means, allowing both or neither; preserve settled requirements. A reply that only identifies the target does not choose what should change there: if the result remains open, ask about that same target and one visible difference. Use Get Clear’s questioning method when available, and never turn a local answer into whole-design approval.
- **Consequential uncertainty:** identify the two plausible revisions and the missing distinction that changes which one you would make. Diagnose measurable failures first; ask only about the remaining preference.
- **Enough context for a reversible comparison:** use a focused visual comparison to resolve the uncertainty within the authorized scope. If the user has requested drafts or delegated the open taste choice, proceed under explicit assumptions without asking for that permission again. Prior references or a bare “continue” do not override an unresolved clarification-first request.
- **Mixed feedback:** keep an independent explicit repair on its direct route, outside the report for the uncertain revision. Operations within the clarified revision wait for report approval; neither an unrelated fix nor a technical diagnosis approves the open direction.
- **User stops:** stop the requested iteration. Preserve unresolved dissatisfaction and the stopping reason; do not seek one more answer or interpret exhaustion as approval.

Do not repeat answered preferences or require library names, CSS values, or professional design decisions. If answers conflict, name the specific conflict rather than quietly discarding an earlier constraint.

## Choose the next useful comparison, not the next question by habit

Before another round, identify what the last answer changed and what the next answer will change. If neither is concrete, synthesize what is known and change the method rather than rephrase the same question. This is an information-gain check, not a fixed round quota or permission to claim understanding prematurely.

In this fallback, draft the exact user-facing question and every tool option before sending. Check that factual claims match the inspected screen and brief, constraints and capabilities stay intact, and the options ask one visible result distinction rather than diagnose its cause or recommend a taste. The answer updates only that distinction; it is not approval of a full redesign. If any check fails, revise the prompt first. When Get Clear owns the interview, use its per-turn check instead of this fallback check.

Ask about recognizable results using the current screen, an action or comparable examples. Group independent questions or references when they are easier to judge together; use one-at-a-time questions when an answer genuinely determines the next branch. Get Clear's one-question rule takes precedence when it owns the interview. Do not recommend an answer to an unresolved taste question or present your causal hypothesis as the user's feeling. Once the desired effect is established or taste is explicitly delegated, recommend implementation choices with their basis. Allow combinations, rejection of every option, and “I cannot describe it.”

For an in-depth interview, keep a compact map of confirmed decisions, consequential open branches and dependencies. Use existing product facts; do not invent an exhaustive specification. After each answer, update the affected branches rather than restart the survey. Workflow answers establish constraints, not visual agreement. A request for design cannot be completed by learning the workflow alone.

Distinguish a **scope answer** from a **direction answer**. “Both appearance and information organization,” “desktop only,” and “keep simultaneous comparison” tell you what must change or survive; they do not choose typography, surface character, spatial relationships or motion. After repeated overall rejection, name what is still open and ask the next consequential question or use an explicitly authorized visual comparison. Do not mark clarification complete because the user selected the broadest option in one question. A useful next prompt points to a difference actually visible in the viewed examples: “Here each item sits in its own outlined area; there the same items form one continuous list. Which feels closer to what you want to look at, or neither?” Do not invent examples, make one deliberately worse, recommend the user's answer, or assert that these are the only options. If words still produce no recognizable difference, show the existing references being compared rather than repeat new labels.

When the answer is needed, ask and wait. Do not use an asynchronous question as a notification while independently implementing one possible answer. If the user cannot judge from words, inspect and show relevant existing references at the [current choice checkpoint](layered-design-selection.md#choice-checkpoints), naming the visible difference being compared. Reading or showing an existing reference is different from producing a new design study. If existing material cannot show the one distinction, a temporary local comparison that changes only that dimension may be made within the current authorized task: leave the business artifact untouched, present it only to clarify the question, and do not imply acceptance of a design. It needs no separate permission. A full mockup, motion sample or concept still needs a concrete comparison scope and authorization; uncertainty alone does not supply either. Existing authorization to make the relevant drafts or decide taste remains valid. Keep following the unresolved distinction until the user confirms the concrete interpretation or explicitly delegates/requests drafts; there is no fixed interview length.

For this reference-only clarification, stop acquiring references as soon as inspected, accessible material supports the next recognizable question. One existing reference compared with the current screen can suffice; this is not the production creative pass or technology selection and does not require the five-source inspection. Show the material through the host's existing image/file/link surface instead of building a comparison website or starting another preview merely to ask. An inaccessible source is a reason to change the acquisition route, not to inspect a succession of unrelated sites or troubleshoot their overlays. State a real evidence gap if it remains; keep the user's preference unresolved. The full design research and implementation requirements still apply when that phase is authorized.

The batch requirement applies to an authorized production design study after the working direction is selected. For a clarification question, use the current artifact or references first; if they do not expose the unresolved distinction, a temporary local comparison may change only that one dimension, as described above. Do not expand that question into a batch or full design pass. In the production study, use a small, professionally developed **batch** of numbered visual alternatives with the same representative content, viewing scale, and ordinary action state. Compare actual combinations of typography, icons, spacing, surfaces and controls; do not ask the user to evaluate “round corners” in isolation. A motion question needs an accessible normal-speed previsualization, not only stills. Do not deliberately weaken an option to make your preferred one win. Reuse relevant selected references instead of sending the user through an endless sequence of unrelated screenshots.

New pages and substantial redesigns default to [progressive design and layered selection](layered-design-selection.md): compare the unsettled aspect in context, then refine one integrated key-page sample before expanding the full implementation. Structure, type, data and important motion can be explored together; a selected skeleton is not approval of unseen components. Bounded playable samples may use real React/UI/chart/GSAP code within the authorized prototype scope without rebuilding business APIs, persistence or switching the normal entry. Do not restart settled layers or demand verbal certainty about qualities that must be seen. A design choice, approval of a draft, and acceptance of its implementation remain distinct.

Keep evaluation axes separate when the user's feedback distinguishes them: attractiveness, recognizable design character, perceived generic/AI-like appearance, and ease of use can disagree. “Not AI-like” does not mean “beautiful”; “AI-like is acceptable” does not waive design quality. A preference for rich icon/label combinations does not authorize arbitrary decoration, game controls or new features.

Method basis: [GRILL-ME's prerequisite-aware method](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/productivity/grilling/SKILL.md) and [usage guidance](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/docs/productivity/grill-me.md). This adaptation retains dependent follow-ups and confirmation, while choosing conversation or visual comparison from the current task and permission. It does not require that external Skill.

## Return according to the decision actually made

Retain a short brief in the existing task context: objective, decisive original wording, rejected and retained qualities, exact selected reference/state and caveat, proposed change, remaining assumptions, and the ordinary action that will reveal it. Apply the [concrete-reference method](open-source-ui-sources.md#preserve-concrete-reference-evidence). Separate confirmed preferences, observed traits and proposed adaptations; no new dossier or permanent preference file is required.

- **Requirement report:** after all consequential preference branches are clear, give the user a sufficiently detailed, task-specific report in the current conversation: goal and key meanings, intended changes, what to retain or exclude, scope and factual constraints, remaining open items, and how the result will be checked. Mark user decisions, sourced facts, and the Agent's proposals/assumptions separately; do not pad the report or present a proposed method as the user's decision. Ask whether it matches the user's intent and is complete. If a consequential point is still unresolved, continue clarifying rather than label the report complete. A long report may also be saved to a suitable file with a real link, while remaining reviewable in this conversation; no new task, window, or PromptReady handoff is required.
- **Report approved:** only explicit approval of the current complete report authorizes implementation of that revision. A correction, added preference, or approval of one item changes the report but does not approve it; preserve settled parts, reopen only affected points, and present the updated report for approval. A separate independent explicit small edit uses the scoped-repair path above instead and does not enter this report. Explicitly stopping or changing the process remains the user's choice.
- **Comparison or taste delegation authorized:** state the open assumptions and deliver the bounded drafts or previsualization requested. This is a valid stage exit, not complete understanding or final acceptance. Do not keep an earlier interview mandate alive against a later explicit instruction to show alternatives. Return to only the distinctions the resulting feedback leaves unresolved.
- **Implementation authorized:** after explicit approval of the report, follow `../SKILL.md` and the [integrated-sample boundary](layered-design-selection.md#build-one-integrated-key-page-sample). Agreement on adjectives, a workflow, or one animation does not approve an entire application. Feasibility and presentational code may support an authorized isolated comparison before full design confirmation; label simulation and keep that work separate from business features, persistence and the normal entry. Then implement only the approved scope; applicable prior designs or explicitly delegated decisions need not be reconfirmed. Do not impose this report gate on an independent direct repair outside the revision being clarified.
- **Stopped without acceptance:** retain that status and cease the UI iteration. No automatic integration, new trial, or success claim follows from “leave it there.”

Preserve the user's clarification-first request, subsequent changes to that request, confirmed answers and unresolved assumptions in an authorized handoff. Do not turn a project preference into a universal rule. If the next result is rejected, investigate that remaining difference rather than defend library coverage.

## Worked examples

**“动画还是没有高级感.”** If inspection shows only panel fades and list scrolling, distinguish barely perceptible change, discontinuity, unrelated movements, and dissatisfaction with the whole layout. Fix an observed snap directly. For “每个部分各动各的,” compare coordinated selection → contextual editing → completion using the [motion sequence method](motion-scroll-and-3d.md#design-a-sequence-not-a-tween-quota), not longer fades. If the layout itself is rejected, use the [composition method](page-composition.md#repair-a-rejected-layout-family).

**“分区清楚，但不要割裂.”** Retain both requirements. Compare the same populated work state with clear local surfaces and shared alignment/type/action relationships. Removing all boundaries answers only half the brief; giving every region identical framing can fail it too. Neither rectangles nor cards are automatically the defect.

**“我说不清，先给我几稿.”** When this explicitly changes an earlier interview request, use known constraints to show coherent alternatives, stating unresolved taste assumptions. Do not continue asking for design vocabulary or claim that permission to compare is design approval. Refine and confirm the representative design before full implementation.

**“外观和布局都要重做，用新版再来.”** This rejects both aspects; it does not say which replacement looks right. Recover the actual rejected artifacts and any retained preference. Ask the remaining visual distinction with concrete references, then develop the selected study; if the user instead explicitly requests a batch or delegates the choice, follow that request. Do not silently translate this scope answer into “a pale list versus dark cards” or treat a past “B is better” as current approval after B was rejected.

**“这个标题被挡住了，移开图标.”** Inspect and repair the overlap and its affected state. A prior broad design complaint does not turn this explicit correction into another interview.

**“一般，但没时间再改了.”** Record a usable candidate only if usability was checked, and separately record unmet design expectations and the user's decision to stop. Do not request another comparison, switch the normal entry, or present the case as a design success.
