# Motion vocabulary: from a named effect to a real interface

Read this when naming an observed effect, finding candidates for a motion relationship, or adapting a Motion Prompt example. It supplements [motion, scroll and 3D](motion-scroll-and-3d.md); that file still owns runtime selection, sequence design, state continuity and performance. This catalog is an on-demand reference, not another mandatory website in the five-source pass, a component system, or a reason to animate every surface.

## Translate the reference into the existing sequence

1. **Start with the real change.** Identify the object, trigger, initial state, user's next action and final state. For an ambiguous desired impression use the existing clarification route. A precise “expand this thumbnail into its detail view” request can go directly to a shared-element candidate.
2. **Choose and observe candidates.** Search by the relationship, read the chosen spec and inspect its live demo. Compare nearby candidates only where they resolve a design choice. State the recognisable mechanism: fixed mask with moving text, actual panel allocation with displaced neighbors, or one image maintaining identity across layouts. An effect name alone leaves too much to guess. Follow the existing [demo-access exception](source-library.md#demo-first-adoption-contract) if playback is unavailable; specs and ordered frames do not prove motion feel.
3. **Carry the mechanism into this product.** Specify the object/property that persists, what moves or is revealed, causal order, relative timing and settled appearance. Use source numbers for a faithful reproduction when requested; otherwise adapt distance, duration and easing to the real dimensions and content, and record the meaningful departure. Keep the required reference character, not incidental colors, fake metrics or looping resets.
4. **Assign one owner.** Keep Ant Design/current permitted primitives for control semantics, GSAP with `@gsap/react` as the default coordinated-motion owner, ScrollTrigger for choreography, and Lenis for eligible scroll mechanics. Canvas examples describe drawing; they do not replace DOM controls. CSS perspective tilt or an isometric exploded drawing does not pass the true-3D suitability gate. Do not install the upstream Skill or a new engine just to use a term.
5. **Complete the sequence's boundary states.** Decide what happens on fast repeat, reversal, resize, route change/unmount and relevant async failure. Continue from the current pose rather than resetting to a template pose. Keep one source of truth for route, selection, request and focus. Reduced motion must reach the same useful final state; content must remain available when nonessential effects cannot run.
6. **Verify the actual adaptation.** At the real entry, watch normal-speed input → visible response → intermediate relationship → settled state, then exercise the affected interruption and fallback. A valid name, imported package, screenshot or timer ending successfully is not this check. Use the [catalog adaptation checks](visual-qa.md#check-a-catalog-adaptation) and retain the outcome in the existing capability/reference record, not a second report.

A sufficient note fits the existing record: “161 shared element; selected thumbnail → detail; same asset and crop stay continuous while nearby labels leave, then detail copy appears; GSAP owns geometry, router owns location; reverse uses current pose; reduced motion opens readable detail; observed at [entry/actions].” Until implemented and watched, label it a proposal.

For a claimed completed catalog adaptation, the existing record must identify the chosen ID, the retained mechanism, the actual artifact/entry and the observed action/outcome (or the precise unverified portion). Without that connection, the deliverable is still research or a proposal. This check applies to a selected catalog adaptation, not unrelated UI work, and adds no approval round.

## Mechanisms and common translation mistakes

These are adaptations derived from the source specifications and UI Done's existing contracts. They are not claims that the catalog's Canvas demos implement production semantics. Inspect the exact chosen entry for the complete original specification.

### Reveal, hierarchy and readable text

- **005 Mask reveal / 133 Text mask / 146 Scroll text reveal are different.** 005 moves text past a fixed clipping edge without changing its opacity; 133 makes letters the viewing window for imagery; 146 starts with visible light-gray text, darkens it character by character as scrolling advances, and restores the light color in reverse order when scrolling back. Preserve the selected relationship; a deliberate product adaptation should record its departure. A generic fade does not reproduce all three. Keep accessible, selectable text where needed and expose complete content in reduced motion or when enhancement fails.
- **002 Stagger and 121 Anticipation establish order.** Stagger related items in a meaningful reading/action sequence. Anticipation may communicate the direction of an expressive move; it should not delay recognition of an ordinary click. 122 Follow-through belongs to parts attached to the moving subject; unrelated decorations following a timer are not the same causal relationship.
- **006/008/129–132 type effects need actual text support.** Do not repeatedly scramble a status or animate every paragraph. A variable-font effect needs a font that really supports the selected axis; reserve layout and check long labels. Source font choices do not override the font/packaging contract.
- **009–015/123–128 motion detail is conditional.** Bounce, squash, trails, paths and pulses can explain material response or emphasize a content object. Compare their contribution against the strongest alternative: a simpler continuous move may make the task clearer. Do not equate greater displacement, more particles or longer duration with a stronger design.

### Controls, layout and actual results

- **049–055/067/162 overlays:** modal, drawer, bottom sheet, dropdown, tooltip, popover and lightbox have different placement and interaction contracts. Preserve focus return, dismissal and stacking behavior of the semantic owner. Choose an anchor and origin where meaningful. 162 should return to the originating thumbnail and preserve the underlying scroll position; image loading and Escape/close during opening need explicit completion.
- **052 Accordion / 057 Tabs / 060 Segmented control:** opening an accordion allocates real space and moves following content; scaling a picture over its neighbors is not equivalent. Coordinate tab indicator position/width, labels and the actual panel. The source segmented-control chart uses staged data; the product's query/filter state must still own the real data. Check interruption and variable content heights.
- **061 Filter chips / 058 Carousel / 063–066 navigation:** fading nonmatching cards in the demo does not decide whether a product should hide, remove or retain them. Use the actual filter meaning, focus order and selection; keep navigation destinations and item counts real. Do not translate an autoplay loop into forced user navigation.
- **069 Skeleton / 070 Spinner / 056 Toast / 089 Preloader / 160 Loading button:** source loops advance by time and may manufacture completion. In a product, the request result owns success/error and the indicator reflects what is actually known. Skeleton geometry reserves the real content layout. Do not fabricate percentage progress or delay a finished result to complete a showcase. Include pending, error/retry and relevant repeated-click handling.
- **160 Loading button detail:** its visual face can shrink and change shape, but keep the semantic hit/focus target stable and prevent re-submission according to the real action. Handle long labels and restoration. A timed check mark is acceptable only as a clearly labeled prototype fixture, never proof a real action succeeded.
- **158 Floating label / 159 Inline validation / 166 Like button:** labels remain associated with their fields and settle on focus or nonempty input. Validation follows the product's policy, not the demo's arbitrary character count; account for composition input and stale asynchronous responses. Optimistic likes require real persistence and a failure rollback when applicable.

### Scroll, pointer and ambient behavior

- **073/076/077/078/093:** parallax, pinning, horizontal scroll, scroll snap and smooth scroll solve different problems. Pin only a meaningful section; derive travel from actual overflow. Mandatory snapping can strand long content or zoomed text. Do not create fake page length or introduce another smoothing owner. Preserve anchors, nested controls and ordinary navigation.
- **074/090/091:** the source resets reveals/lazy loading/infinite content for replay. A product should not unload fetched content or repeatedly hide text because the user scrolls back. Real infinite loading needs pending, error, retry, end-of-list and appropriate return-position handling; a repeated set of Canvas cards is not pagination.
- **145/147–152/167:** timelines use real milestones; stacked cards must not permanently occlude required content; background transitions must retain contrast; an auto-hiding header must not hide focused navigation. Scrollspy follows real headings, back-to-top has an appropriate target, and a cue must point to actual continuation. Scroll zoom cannot make required controls unreachable.
- **081–086/153–157:** hover lift, zoom, follower, magnetic face, ripple, underline, tilt, spotlight, image swap, text roll and hover image reveal are distinct visual responses. Keep the clickable/keyboard target stable; bound the face's motion and return from its current pose. Use frame-time-independent interpolation for follower/lag behavior. Do not hide essential text, actions or meaning behind hover alone.
- **087 Before/after / 163 Hotspots:** align real corresponding subjects and expose equivalent labeled controls. A wipe between unrelated pictures does not substantiate an improvement; a hotspot's visible position must remain attached to its actual feature across sizes.
- **088/094–096/164–165/168:** exit-intent promotion requires an actual product brief; an animation reference is not authorization for a popup. Marquee, gradient and floating loops need bounded/visibility/reduced-motion behavior. Countdown derives from an authoritative deadline and time zone. Video backgrounds need appropriate poster, loading/failure and playback handling. Shape dividers belong to the layout and must not cover content.

### Transitions, media and space

- **092 Page transition:** a covering layer hides the old→new scene replacement, then clears. Keep route loading/error/abort and rapid navigation owned by the real router; cleanup must not leave a full-page layer intercepting input. Do not switch content in plain view if the agreed mechanism requires it to be covered.
- **161 Shared element:** preserve the same object through list→detail geometry, crop and context change. The source image travels between differently proportioned allocations while old context leaves and new text enters later; reproducing only two disconnected fades loses identity. Measure the real layouts, preserve the asset's crop intentionally, handle return and retarget from the current visual pose. A browser View Transition API is a possible mechanism, not a required replacement for the Skill's GSAP owner; check ownership and current API support before adoption.
- **017–021/137–144:** mask, shape, liquid, zoom-through, flip, push, blinds, cube, page curl, pixelate and shatter make different scene relationships. Choose their content reason before surface style. Exploded view explains parts; split screen explains simultaneous views. The source's isometric drawing is not proof of real spatial geometry or WebGL use.
- **025–048/169–192 and 097–120:** keep camera translation distinct from lens zoom, depth of field distinct from blur decoration, and editing order distinct from DOM state. Use camera/photography entries for the media or scene actually in scope. A J/L cut concerns audio/video overlap; backlighting or duotone concerns imagery. Neither alone satisfies a UI interaction-motion requirement.
